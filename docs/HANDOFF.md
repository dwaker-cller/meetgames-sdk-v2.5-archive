## 2. 我们正在做什么

这是 MeetGames 发行服务 SDK 管理工具的离线 Web 交互 Demo，主要用于产品方案展示、领导评审和研发需求澄清。当前工作分为两个阶段：

Demo 不是生产系统。它没有真实后端、权限、审计、远程配置服务、原生 SDK 二进制、第三方平台真实联调，也没有可作为生产依据的安全存储方案。PRD 不能把浏览器本地状态或模拟下载直接写成最终技术架构。

## 4. 当前已确认并实现的产品逻辑

### 4.1 两层状态必须分开

这是整个产品最重要的概念，PRD 必须明确：

- 配置中心：保存游戏级、可复用的 SDK 参数，可以同时存在多个平台的配置或半成品。
- 生成 SDK：为某个发行渠道的某个 SDK 组合包，选择本次真正打包的能力和平台。

“配置了某个平台”不等于“当前组合包一定包含该平台”。不要再把配置中心的展示/配置状态与组合包选择状态合并。

### 4.2 配置完整度与部分保存

支付、登录、协议与隐私、合规、归因数据、广告变现、客服工具均遵循：

- 用户可以保存填写到一半的参数，关闭后再次进入仍能看到已填写内容。
- 缺少必填项的最小配置单元不可在生成 SDK 时选择。
- 已完整配置的最小单元仍可使用，不应因为同一能力下另一个平台未完成而整体失效。
- 字段格式错误应在字段下方显示红色说明，例如要求 URL 以 `https://` 开头。
- “可保存半成品”与“可用于出包”是两个不同判断，不能共用一个布尔状态。

当前归因数据/广告变现的就绪逻辑是：至少有一个平台完整即可让该能力出现可选平台；未完成的平台保留数据但不进入本次可选范围。

### 4.3 配置中心平台展示

当前 update=54 的视觉形态：

- 归因数据：Firebase、AppsFlyer、Adjust 三张横向卡片，同一行展示。
- 广告变现：Google AdMob、AppLovin MAX 两张横向卡片，同一行展示。
- 平台卡不显示右上角小对勾；紫色边框表示当前展开/选中展示。
- 用户可以展开一个、多个或全部收起；收起不等于删除已经填写的参数。
- 当前不是下拉框形式；update=47 的下拉设计已经回退。

这里仍有需要 PRD 拍板的语义：平台卡点击究竟只是“展开/收起参数面板”，还是持久化的“启用/停用平台”。当前 Demo 更接近展示状态；只要某平台已有输入值，重新进入时仍可能根据已开始配置的值显示它。PRD 必须给它一个唯一、稳定的定义。

### 4.4 生成 SDK 抽屉

当前已完成的交互：

- 标题为“生成SDK”。
- 抽屉内 SDK 能力区每行两张紧凑卡片。
- 共七种能力：登录、支付、协议与隐私、合规、客服工具、归因数据、广告变现。
- 已成功配置的普通能力可勾选；登录/支付优先用平台 Logo 展示已配置内容，其他普通能力显示简短摘要。
- 未达到可用条件的能力显示“待配置”和“前往配置”，不能直接勾选。
- 未选择发行渠道时，七张能力卡仍直接展示已有配置摘要或“待配置”，但所有能力均保持禁用；选择发行渠道后才允许勾选能力或平台。
- 点击“前往配置”打开的界面与配置中心对应能力卡片使用相同的页面表现和保存逻辑。
- 支付卡有渠道说明：支付 SDK 仅在对应发行渠道生效，其他支付渠道的配置不生效。
- 归因数据、广告变现没有外层能力勾选框；内部平台按钮的选中状态决定该能力是否进入组合包。
- 平台按钮内部有小勾选框，紫色边框表示被选入本次包。
- 归因数据中 Firebase 可与其他平台共存；AppsFlyer 与 Adjust 互斥。
- 广告变现中 Google AdMob 与 AppLovin MAX 互斥。
- 新建组合包时，默认选择当前已完整配置的首个可用平台组合。
- 保存/生成的包快照只包含本次选中的、已经完成的最小配置单元；未选或未完成平台的参数不应混入下载快照。

### 4.5 登录与支付的特殊规则

登录：

- Guest 默认必选。
- Email、Apple 为无需参数的方式。
- 其他登录方式根据平台和系统维护参数。
- 登录方式选择弹窗在有改动时关闭，会出现保存/不保存/取消提示。
- 生成 SDK 抽屉里的登录“前往配置”与配置中心登录使用同一套界面和逻辑。

支付：

- 每个发行渠道分别判断支付参数是否完整。
- 可以保存不完整的渠道参数并在下次继续。
- 生成 SDK 时，只有当前所选发行渠道的支付配置完整，且通用发货地址等必填字段合法，支付能力才可选择。
- 其他渠道即使完成，也不能替代当前渠道的支付配置。

### 4.6 未保存提示与线上风险提示

## 6. 当前卡在哪里

没有代码层面的硬阻塞；当前“卡点”是产品定义还没有完全冻结。领导的逐条反馈已经形成可演示的 Demo，但以下问题如果不先写清，研发会遇到状态模型和验收口径冲突：

1. 配置中心的平台卡点击，是纯展示控制，还是持久化的启用状态？
2. AppsFlyer/Adjust 和 AdMob/AppLovin 最终是否允许二选零？当前文案说二选一，交互允许最后一个取消。
3. 同一能力下只有一个平台完整、其他平台半成品时，是否明确按“至少一个完整平台即可用”处理？当前 Demo 是这样做的。
4. 生成抽屉草稿是否要跨浏览器刷新、跨设备、跨账号保留？当前 React 表单刷新会丢失，运营策略 localStorage 会保留。
5. 归因、广告、客服在运营区是只读包快照，还是要提供二次编辑能力？
6. 保存配置后，已有组合包如何计算受影响范围，是否立即生效，是否需要重新生成、灰度或回滚？当前只有通用风险提示。
7. 文件上传、密钥、敏感参数在生产环境如何存储、加密、校验、版本化和审计？Demo 只有浏览器侧模拟。
8. 角色权限、审批、操作审计、并发编辑、API 错误、加载态、空态、国际化和无障碍尚未形成正式规则。
9. “包名”到底是下载产物名称，还是 Android `applicationId` / iOS Bundle ID？当前 Demo 按应用身份字段处理并允许在重新生成时修改；正式产品必须明确。若它代表 `applicationId` 或 Bundle ID，修改通常意味着新的应用身份，不能被当作对线上原包的普通无风险更新。

这些问题应成为 PRD 的“待确认决策”，不要由开发或下一次对话擅自假设。

## 7. 下一步计划：编写面向研发的 PRD

### 7.1 建议执行顺序

1. 以本交接文档和 update=54 实际页面为基线，建立“页面现状 / 产品最终规则 / 待确认项”三列表，避免把 Demo 偶然实现写成需求。
2. 阅读旧 V2.2 PRD，只提取仍有效的背景、角色和术语；逐条核对本交接中的最新规则。
3. 先确认第 6 节的状态模型决策，尤其是配置中心展示状态、平台启用状态、组合包选择状态三者的关系。
4. 编写 V2.4 PRD，至少包含目标、范围、角色、术语、信息架构、核心流程、状态模型、字段校验、保存/风险规则、组合包规则、权限与审计、异常状态、非功能要求、数据/API 需求、验收标准和不在范围内事项。
5. 为七类 SDK 能力分别列出“最小可用单元、完成条件、允许半成品保存、在生成 SDK 中的可选条件、风险影响范围”。
6. 把未确认问题单独放在“产品决策清单”，先与领导确认，再把答案合并到正式验收标准。
7. PRD 完成后，再生成研发验收标准和边界用例；不要先按当前 DOM 写实现级规格。

### 7.2 PRD 必须包含的状态模型

建议明确以下至少四个状态，而不是一个“已配置”字段：

- `draft/started`：用户已经输入但尚未满足完整条件。
- `complete`：某个最小配置单元满足格式和必填要求。
- `available`：对当前发行渠道和当前生成上下文可供选择。
- `included`：已经被选择进入某个具体 SDK 组合包。

另把 `expanded/visible` 作为纯 UI 状态。这样可以解释“配置写了一半仍保存”“平台收起不清数据”“完成的平台可以出包”“配置中心完成但当前包不一定包含”。

### 7.3 建议 PRD 验收主线

- 没有组合包时：填写半成品 → 关闭 → 普通保存提示 → 保存后重开数据仍在 → 未完成单元不能选择出包。
- 有组合包时：修改参数 → 直接风险提示 → 返回检查/不保存/确认风险并保存三条路径都能恢复到预期状态。
- 同能力多平台：一个平台完整、一个半成品 → 完整平台可选，半成品不可选，半成品数据仍保留。
- 渠道切换：支付仅按当前渠道完整度决定可用性，其他渠道配置不串用。
- 组合包快照：只包含实际选择并完成的能力/平台，不泄露未选平台参数。
- 新建组合包：提交后立即下载有效 ZIP，列表只新增一个对应渠道组合包。
- 重新生成：预填原包名和能力；修改后保持原组合包 ID、渠道和运营配置，列表行数不变，生成时间与 ZIP 内容更新。
- 包名独立保存：合法包名即时更新列表，但不得刷新生成时间、写入 SDK 能力、改变上次生成快照或触发下载；未保存的 SDK 改动仍需提示。
- 草稿隔离：已有新建草稿时进入、退出或完成重新生成，新建草稿均不得被覆盖。
- 刷新、重复打开、取消、风险不保存、快捷配置与配置中心之间的状态一致性。

## 8. 工程结构与修改方式

这不是一套干净、可重新构建的现代源代码仓库。当前权威页面主要由已编译 React chunk、CSS 覆盖和 DOM/localStorage 增强组成：

- `_next\static\chunks\1uxbj6ciunkfi.js`：配置中心、生成抽屉、组合包、风险弹窗等核心 React 逻辑。
- `demo-sdk-card-redesign.css`：大量最终视觉覆盖。
- `demo-country-strategy.js` / `.css`：运营策略工作台、localStorage 和 DOM 桥接。
- `sync-v2-static-entry.cjs`：把运行态同步到静态入口并更新资源缓存标记。
- `index.html` / `打开Demo.html`：必须保持一致的两个入口。

根目录较早的 `app/`、`public/`、`package.json` 与当前交付 chunk 已有明显漂移。不要直接运行旧 Next 构建并覆盖工作台，否则会回退大量已验收能力。

修改原则：

- 只在权威开发工作台改，不直接编辑 backups 或 deliverables。
- 修改前在工作台 `.rollback` 下建立有明确时间和目的的快照。
- 对编译 chunk 做尽可能小、可定位的补丁。
- 修改 JS 后至少执行 `node --check`；然后同步两个 HTML 入口。
- 每次用全新浏览器上下文测试，不能只依赖已经打开、带旧 localStorage 和缓存的页面。
- 更新内部资源查询串；仅修改地址栏 `?update=` 不能保证 CSS/JS 缓存失效。
- 普通改动完成后不要自动生成交付包，等待用户明确授权。

## 9. 已踩过的坑与注意事项

### 9.1 React hydration 不会自动修补所有 SSR class

配置中心归因卡曾出现：源码计算为 configured，但新页面仍沿用 SSR 灰色 class。React 生产模式只报告 hydration mismatch，未必修改初始属性。最后用 CSS `:has(.mgp-config-card-summary)` 兜底。验收必须看 fresh context 的真实 computed style，不能只 grep JS。

### 9.2 配置状态与包选择状态容易互相污染

历史实现曾同时用顶层 `includedCapabilities` 和平台字段表达归因/广告选择，造成无法自然实现“二选零”和旧草稿状态冲突。现在平台字段决定归因/广告是否进入包。PRD 和后端数据模型必须保留这种分层，不要重新合并。

### 9.3 收起平台不能清空参数

配置中心的平台选择主要服务于展示和继续编辑。用户明确要求可以一个、多选或不选；不选并不表示删除参数。若产品最终需要“停用并清除”，必须是单独、明确、带确认的操作。

### 9.4 风险提示与普通未保存提示不能叠加

已有发行渠道 SDK 包时只出现风险提示；没有包时才出现普通未保存提示。不要恢复成“普通未保存 → 再风险确认”的两层弹窗。

### 9.5 旧 QA 脚本不全是当前真相

工作台中的 `qa-sdk-card-smoke.cjs`、`qa-v2-sdk-download.cjs`、`qa-v2-generation-operations.cjs` 等脚本包含旧页面结构或旧产品规则。运行前必须先审查断言，不能因为脚本失败就直接回退当前行为，也不能因为旧脚本通过就认定新需求通过。

### 9.6 两个入口和缓存标记必须同步

每次正式改动后都要核对：

- `index.html` 与 `打开Demo.html` hash 一致。
- HTML 引用的 CSS/JS 查询串是当前版本。
- HTTP 入口和 `file://` 入口都能打开。
- 交付目录不包含临时 QA 文件、截图、同步脚本或测试下载包。

### 9.7 Demo 上传并非生产文件系统

Firebase 等上传目前主要保存文件名、元数据和浏览器侧 SHA-256；没有真实二进制持久化、服务端扫描或第三方验证。历史默认文件可能没有 SHA，因此第一次替换会触发保守风险判断。PRD 需要定义生产上传、存储、替换、回滚和权限规则。

### 9.8 运营策略和 React 状态并非同一存储

运营策略依赖 localStorage，生成抽屉表单主要是 React 页面生命周期状态。刷新后两者的持久化表现不同。正式产品必须由 PRD 定义服务端草稿与已发布配置，不能照抄 localStorage 行为。

### 9.9 不要泄露参数和密钥

Demo 中有示例参数。交接、PRD、截图和日志只描述字段名、掩码和状态，不复制实际 Client Secret、SDK Key、共享密钥、上传文件内容或其他敏感值。

### 9.10 工具环境细节

- 当前端口 4173 在交接时可用，但下次仍要验证。
- 临时回归服务常用 4174，测试结束后应停止，避免残留监听。
- 本环境中 `rg.exe` 偶尔会出现 Access Denied；可改用 PowerShell `Select-String` 和 `Get-ChildItem`。
- 工作区可能存在用户自己的历史文件和未跟踪内容；不要执行 `git reset --hard`、大范围清理或覆盖无关文件。
